# Архитектура и проектные решения

Документ фиксирует решения, принятые при доработке ТЗ (`docs/01-tz.md`), и служит контрактом для разработки сервера и интерфейса. Там, где ТЗ оставляет вопрос открытым, здесь выбрано значение по умолчанию для тестовой модели; все такие места помечены **[решение]** и могут быть пересмотрены заказчиком.

## 1. Состав системы

| Компонент | Технологии | Каталог |
|---|---|---|
| Сервер (API, бизнес-логика, фоновые задания) | Node.js 22, TypeScript, Fastify 5 | `server/` |
| База данных | PostgreSQL 16, SQL-миграции | `server/migrations/` |
| Хранилище файлов | Каталог на диске сервера (`FILES_DIR`), имена — случайные идентификаторы | — |
| Интерфейс | React 18, Vite, TypeScript, React Router, обычный CSS | `web/` |
| Интеграция с Битрикс24 | Адаптер с двумя реализациями: `mock` (встроенный эмулятор) и `rest` (входящий вебхук REST API) | `server/src/bitrix/` |
| Развёртывание | Docker Compose (приложение + PostgreSQL), скрипты резервного копирования | `deploy/` |

Один процесс сервера отдаёт API (`/api/*`) и собранный интерфейс (статические файлы `web/dist`). Состояние хранится только в PostgreSQL и каталоге файлов, поэтому резервная копия = дамп базы + архив каталога файлов + файл настроек.

Нагрузка (500 сотрудников, до 150 одновременных) для такого состава невелика: один экземпляр приложения и пул из 20 соединений с базой. Все списки — с разбивкой на страницы и индексами по полям фильтров.

## 2. Ключевые решения по открытым вопросам ТЗ

1. **[решение] Режим маршрута** выбирает инициатор при запуске; по умолчанию — последовательный. Режим хранится в запуске (раунде) согласования.
2. **[решение] Отрицательное решение завершает раунд сразу.** «Вернуть на доработку» → статус «На доработке», «Отклонить» → «Отклонено» — и в последовательном, и в параллельном режиме. Шаги участников, не успевших ответить, получают состояние «Не потребовалось».
3. **[решение] Повторный запуск** создаёт новый раунд для всех согласующих (правило ТЗ 8.4). Решения привязаны к раунду, раунд — к снимку версий файлов на момент запуска.
4. **[решение] Файлы заблокированы во время согласования.** Загрузка новой версии, добавление и удаление файлов возможны только в статусах «Черновик» и «На доработке». Так выполняется требование 13.2 о запрете незаметной замены.
5. **[решение] Уполномоченные пользователи.** Отменить согласование и изменить маршрут может инициатор и пользователь с системной ролью «Администратор». Заменить можно только участника, ещё не принявшего решение; добавить — в конец маршрута (в параллельном — в группу). Причина обязательна, изменение пишется в историю.
6. **[решение] Системные роли** (назначает администратор, можно несколько):
   - `employee` «Сотрудник» — базовая: создание согласований, приказов и поручений, участие в процессах;
   - `signer` «Утверждающий» — может быть выбран утверждающим приказа;
   - `admin` «Администратор» — пользователи, подразделения, типы документов, интеграция, журнал действий (без доступа к содержимому документов);
   - `auditor` «Контроль документов» — отдельное полномочие на просмотр всех документов, поручений и отчётов по компании (требование 4.2.6: доступ к содержимому — отдельная настройка).
   Роли ТЗ «Инициатор», «Согласующий», «Исполнитель», «Постановщик», «Наблюдатель» — контекстные: определяются участием в конкретной карточке.
7. **[решение] Кто видит карточку документа:** инициатор; согласующие любого раунда; утверждающий; наблюдатели; сотрудники из списка ознакомления (после утверждения приказа); пользователи и подразделения, которым доступ открыт индивидуально в карточке («Доступ»); роль `auditor`. Остальным — 404 «Документ не найден или нет доступа» (не раскрываем существование). Доступ к файлам и истории = доступ к карточке. Сотрудник, участвующий в поручении, созданном по документу, видит только номер и название документа-основания.
8. **[решение] Кто видит поручение:** постановщик, исполнитель, наблюдатели поручения, роль `auditor`.
9. **[решение] Жизненный цикл приказа:** «Черновик» → «На согласовании» (если указаны согласующие) → «На утверждении» → «Утверждён» → «В архиве». Утверждающий может утвердить, вернуть на доработку или отклонить (комментарий обязателен для двух последних). После утверждения автоматически стартует ознакомление; файлы приказа после утверждения не изменяются (новая редакция — новый приказ). Ознакомление фиксирует версию основного файла.
10. **[решение] Нумерация:** `<префикс типа>-<год>-<порядковый номер>` (например, `GPM-2026-000014`), номер присваивается при создании карточки, счётчик — отдельный на тип и год. Поручения: `ПОР-2026-000007`.
11. **[решение] Сроки.** Срок — дата и время (конец выбранного дня). Уведомление «срок приближается» — за 24 часа, «срок нарушен» — при наступлении; каждое формируется один раз на участника, от которого ожидается действие. Просрочка вычисляется, а не хранится.
12. **[решение] Файлы:** до 50 МБ на файл (настройка `MAX_FILE_MB`), расширения `xlsx, xls, docx, doc, pdf, jpg, jpeg, png` (настройка), проверка расширения и сигнатуры содержимого, отдача только через API с проверкой прав, `Content-Disposition: attachment`, `X-Content-Type-Options: nosniff`.
13. **[решение] Блокировка сотрудника:** вход запрещён, сессии сбрасываются, история сохраняется, сотрудник не предлагается в выборе участников. Его незавершённые шаги остаются и видны инициатору с пометкой «учётная запись заблокирована» — инициатор заменяет участника.
14. **[решение] Отображение в Битрикс24:** для каждого согласования создаётся одна связанная со сделкой задача (`tasks.task.add`, привязка `UF_CRM_TASK = ["D_<id сделки>"]`). Название задачи: `[<статус>] <название согласования>`; в описании — ссылка на карточку, номер, инициатор, текущие согласующие, дата создания. Окончательный способ уточняется после обследования кастомизированного Битрикс24 — адаптер изолирует это решение.
15. **[решение] Битрикс24 — только получатель.** Изменение или закрытие задачи в Битрикс24 не влияет на согласование; при следующей синхронизации запись приводится к актуальному состоянию.

## 3. Модель данных (основные таблицы)

- `departments` — id, name, active.
- `users` — id, login (уникальный), full_name, position, department_id, password_hash, roles (text[]), active, must_change_password, created_at.
- `sessions` — id (случайный токен, хранится хэш), user_id, created_at, expires_at.
- `doc_types` — id, code, name, kind (`approval` | `order`), number_prefix, active, настройки обязательности: `require_deal`, `require_file`, `require_excel`, `require_deadline`, `require_description`. Начальные типы: «Согласование GPM-калькулятора» (`GPM`, сделка и Excel обязательны), «Другое согласование» (`СГЛ`), «Приказ» (`ПР`, kind = order).
- `documents` — id, number, doc_type_id, kind, title, description, initiator_id, department_id (подразделение инициатора на момент создания), status, route_mode (`sequential` | `parallel`), due_at, deal_id, deal_title, deal_url, signer_id (для приказов), order_date, created_at, updated_at, launched_at, completed_at.
- `document_participants` — document_id, user_id, role (`approver` | `observer` | `acquaintance`), position (порядок согласующих).
- `document_access` — document_id, user_id | department_id (индивидуальный доступ на просмотр).
- `approval_rounds` — id, document_id, round_no, mode, started_at, started_by, finished_at, outcome (`approved` | `rework` | `rejected` | `cancelled`).
- `approval_steps` — id, round_id, user_id, position, state (`waiting` — очередь не дошла, `pending` — ожидается решение, `approved`, `rework`, `rejected`, `skipped` — не потребовалось, `replaced`), comment, decided_at.
- `round_files` — round_id, file_version_id (снимок версий на момент запуска).
- `files` — id, owner_type (`document` | `task`), owner_id, role (`main` | `attachment` | `result`), title, deleted_at.
- `file_versions` — id, file_id, version_no, original_name, ext, mime, size, sha256, storage_key, uploaded_by, uploaded_at.
- `acknowledgements` — document_id, user_id, acknowledged_at, file_version_id.
- `tasks` — id, number, title, body, author_id, assignee_id, due_at, document_id (nullable — самостоятельное поручение), status, result_text, created_at, updated_at, completed_at.
- `task_observers`, `comments` (entity_type, entity_id, author_id, body, created_at).
- `notifications` — id, user_id, type, title, body, entity_type, entity_id, created_at, read_at, dedupe_key (уникальный, для сроков).
- `audit_log` — id, at, actor_id (null = системный процесс), entity_type, entity_id, action, summary (готовая русская фраза), details (jsonb).
- `bitrix_links` — document_id (уникальный), external_task_id, state (`pending` | `synced` | `error`), synced_status, attempts, last_error, last_attempt_at, next_attempt_at.
- `counters` — key (тип+год), value.
- `settings` — key, value (jsonb): режим адаптера Битрикс24, флаг «эмулятор недоступен» и т. п.
- Эмулятор Битрикс24: `mock_deals` (id, title, stage, company, amount), `mock_tasks` (id, deal_id, marker уникальный, title, description, status, created_at, updated_at).

## 4. Машины состояний

### 4.1. Документ (согласование и приказ)

| Статус | Код | Переходы |
|---|---|---|
| Черновик | `draft` | запуск → `in_review` (или сразу `on_signing` для приказа без согласующих); отмена → `cancelled` |
| На согласовании | `in_review` | все согласовали → `approved` (согласование) или `on_signing` (приказ); возврат → `rework`; отклонение → `rejected`; отмена → `cancelled` |
| На доработке | `rework` | повторный запуск → `in_review`; отмена → `cancelled` |
| На утверждении (только приказ) | `on_signing` | утвердить → `approved`; вернуть → `rework`; отклонить → `rejected`; отмена → `cancelled` |
| Согласовано / Утверждён | `approved` | приказ: в архив → `archived` |
| Отклонено | `rejected` | — |
| Отменено | `cancelled` | — |
| В архиве (только приказ) | `archived` | — |

Проверка перед запуском: название; не менее одного согласующего (для приказа — утверждающий обязателен, согласующие — нет); обязательные поля по настройкам типа (`require_*`); для `require_excel` — основной файл с расширением xlsx/xls. Ответ с ошибкой содержит перечень незаполненного — интерфейс показывает его списком.

Последовательный режим: первый шаг `pending`, остальные `waiting`; после согласования следующий становится `pending`. Параллельный: все `pending`. Инициатор не может быть согласующим собственного документа; один сотрудник — не более одного шага в раунде.

### 4.2. Поручение

`new` «Новое» → `in_progress` «В работе» (исполнитель берёт в работу) → `review` «На проверке» (исполнитель передаёт результат, текст результата обязателен; допускается и из `new`) → `done` «Выполнено» (постановщик принимает) либо обратно в `in_progress` (постановщик возвращает, комментарий обязателен). Из любого незавершённого статуса постановщик может отменить → `cancelled` (причина обязательна). Постановщик может изменить срок и исполнителя, пока поручение не завершено (пишется в историю). Признак «просрочено» = срок прошёл и статус не `done`/`cancelled`.

## 5. Интеграция с Битрикс24

Интерфейс адаптера (`server/src/bitrix/adapter.ts`):

```ts
interface BitrixAdapter {
  searchDeals(query: string): Promise<Deal[]>;          // поиск по названию и номеру
  getDeal(id: string): Promise<Deal | null>;
  upsertApprovalTask(input: {
    externalTaskId: string | null;  // null — запись ещё не создана
    marker: string;                 // "DOCFLOW-<id документа>" — ключ идемпотентности
    dealId: string;
    title: string; statusCode: string; statusLabel: string;
    cardUrl: string; createdAt: string;
    initiator: string; currentApprovers: string[];
  }): Promise<{ externalTaskId: string }>;
  dealUrl(id: string): string;
}
```

Порядок работы:

1. При запуске согласования со сделкой и при каждом изменении статуса в той же транзакции строка `bitrix_links` переводится в `pending`.
2. Фоновый обработчик (каждые 15 с, плюс немедленная попытка после изменения) берёт строки `pending`/`error` с наступившим `next_attempt_at`, блокирует их (`FOR UPDATE SKIP LOCKED`) и вызывает `upsertApprovalTask` с **актуальным** статусом документа.
3. Идемпотентность: если `external_task_id` пуст, адаптер сначала ищет запись по маркеру и только при отсутствии создаёт новую; идентификатор сохраняется. Повторная отправка всегда обновляет ту же запись.
4. Ошибка: `state = error`, текст ошибки, счётчик попыток, следующий автоматический повтор с нарастающей паузой (1, 5, 15, 60 мин), запись в журнал. Статус согласования от этого не зависит.
5. Ручной повтор доступен администратору (экран интеграции) и инициатору (в карточке).

Реализация `rest` использует входящий вебхук (`BITRIX_WEBHOOK_URL`, хранится только в переменных окружения сервера): `crm.deal.list`, `crm.deal.get`, `tasks.task.list` (поиск по маркеру), `tasks.task.add`, `tasks.task.update`. Реализация `mock` работает с таблицами эмулятора и имеет переключатель «Битрикс24 недоступен» для проверки сценария 11 приёмки. Страница эмулятора сделки показывает список задач сделки со ссылками на карточки — это стенд для сценариев 8–11 до подключения боевого Битрикс24.

## 6. Безопасность

- Пароли — scrypt с солью; сессия — случайный токен в cookie `HttpOnly`, `SameSite=Lax`, `Secure` при работе по HTTPS; в базе хранится хэш токена. Срок сессии — 12 часов бездействия.
- Ограничение перебора пароля: 10 неудачных попыток на логин за 15 минут.
- Изменяющие запросы принимаются только с заголовком `X-Requested-With: docflow` (защита от межсайтовых запросов вместе с `SameSite`).
- Проверка прав выполняется на сервере в каждом обработчике; интерфейс лишь скрывает недоступное.
- Авторизация изолирована интерфейсом `AuthProvider` (сейчас — локальные учётные записи) для последующего подключения корпоративного входа.
- HTTPS обеспечивается обратным прокси на внутреннем сервере (пример конфигурации — в инструкции по установке).

## 7. API (обзор)

Все пути — с префиксом `/api`, формат JSON, ошибки — `{ "error": { "code": "...", "message": "русский текст", "details": [...] } }` с кодами 400/401/403/404/409/422. Списки: `?page=&pageSize=` → `{ items, total, page, pageSize }`. Точные типы запросов и ответов — в `server/src/api-types.ts` и `docs/04-api.md` (формируются вместе с сервером и являются источником истины для интерфейса).

| Группа | Маршруты |
|---|---|
| Сессия | `POST /auth/login`, `POST /auth/logout`, `GET /auth/me`, `POST /auth/change-password` |
| Справочники | `GET /users` (поиск для выбора участников), `GET /departments`, `GET /doc-types` |
| Главная | `GET /dashboard` — счётчики и короткие списки «ждёт моего решения», «на доработке у меня», «мои поручения», «на ознакомление», «на утверждение», «просрочено» |
| Документы | `GET /documents` (фильтры: `q`, `scope` = all/mine/to_approve/to_sign/to_acknowledge, `kind`, `typeId`, `status`, `initiatorId`, `departmentId`, `createdFrom`, `createdTo`, `deal`, `overdue`), `POST /documents`, `GET /documents/:id`, `PATCH /documents/:id`, `DELETE /documents/:id` (только черновик) |
| Процесс | `POST /documents/:id/launch`, `/decision` (approve/rework/reject + comment), `/sign` (approve/rework/reject), `/cancel`, `/archive`, `/acknowledge`, `PUT /documents/:id/route` (замена/добавление участника с причиной), `PUT /documents/:id/access`, `PUT /documents/:id/acquaintance` |

## 8. Фоновые задания

Запускаются внутри процесса сервера: синхронизация с Битрикс24 (15 с), проверка сроков и формирование уведомлений (5 мин), очистка просроченных сессий (1 ч). Все задания безопасны для повторного выполнения.

## 9. Что сознательно не входит в тестовую модель

Расчёт GPM и разбор Excel; электронная подпись; почтовые уведомления; единый вход; экспорт отчётов; повторный запуск с отдельного этапа; новые редакции утверждённого приказа; предпросмотр файлов в браузере (только скачивание).

## 10. Уточнения по итогам аналитической проработки ТЗ

Дополняют разделы 2–5 и обязательны для реализации.

**Процесс согласования**

- Решения сериализуются блокировкой строки раунда (`SELECT … FOR UPDATE`). Решение по уже закрытому раунду или шагу не в состоянии `pending` → 409. Повтор того же решения тем же участником (двойное нажатие) не создаёт второй записи.
- Все согласующие считаются обязательными (в ТЗ 10.3 необязательные не определены).
- Комментарий из одних пробелов считается пустым → 422.
- При повторном запуске прошедший срок необходимо обновить (ошибка проверки «Срок уже прошёл»).
- Заменённый участник теряет доступ к карточке, если у него не осталось иных оснований; запись о замене остаётся в истории.
- Изменение маршрута запрещено в завершённых статусах.
- Сделку можно менять только до первого запуска.
- Инициатор может один раз в сутки отправить напоминание участникам, от которых ожидается решение (`POST /documents/:id/remind`).
- Карточку (в том числе отклонённую или отменённую) можно скопировать в новый черновик без файлов и решений (`POST /documents/:id/copy`).

**Приказы**

- Утверждение применяется только к приказам. Связь со сделкой для приказов и поручений не используется.
- Список ознакомления после утверждения можно дополнять, но не сокращать; добавленный сотрудник получает уведомление.
- Ознакомиться можно только с утверждённым приказом; повторное подтверждение ничего не меняет.
- Сводку ознакомления видят инициатор, утверждающий и роль `auditor`. Заблокированные сотрудники исключаются из числа ожидаемых.
- Архивирует инициатор или администратор.

**Файлы**

- Дополнительные лимиты: не более 20 файлов и 200 МБ на карточку (настройки). Файлы с макросами (`xlsm`, `docm`) и несоответствие сигнатуры расширению отклоняются. Превышение размера → 413.
- Проверка антивирусом — точка расширения (интерфейс `FileScanner`, по умолчанию пустая реализация).

**Битрикс24**

- Черновики не передаются: запись создаётся при первом запуске согласования со сделкой.
- Передаётся целевое состояние, а не событие: сколько бы раз статус ни сменился за время недоступности, после восстановления в Битрикс24 окажется одна запись с последним статусом.
- Если запись в Битрикс24 удалена вручную (адаптер сообщает «не найдено») — она создаётся заново; если закрыта при активном согласовании — возобновляется. Оба случая пишутся в журнал.
- Запись завершается (закрывается) при статусах «Согласовано», «Отклонено», «Отменено».
- Из сведений о сделке в карточке показываются только идентификатор, название и ссылка: вебхук работает от технического пользователя, права конкретного сотрудника в Битрикс24 системе неизвестны.
- Переход из сделки по ссылке без активной сессии ведёт на страницу входа с возвратом на карточку (единого входа на первом этапе нет).

**Прочее**

- Учётные записи не удаляются, только блокируются. При блокировке сотрудника с незавершёнными шагами или поручениями инициатор (постановщик) получает уведомление «требуется замена участника».
- Отчёты о нарушенном сроке включают только незавершённые процессы. Отчёты и счётчики строятся строго в пределах прав доступа пользователя — без утечки чужих названий и количества.
- Интерфейс опрашивает счётчик уведомлений раз в 60 секунд (постоянное соединение для 150 пользователей избыточно).
- Отложено на развитие: шаблоны маршрутов, замещение на время отсутствия, экспорт, предпросмотр файлов, роль руководителя подразделения.
