# Изменения, согласуемые на демо-версии

Функциональность сначала дорабатывается и утверждается на автономной демо-версии (`web/src/demo`, сборка `npm run build:demo`), затем переносится в основной продукт (сервер `server/` и интерфейс `web/`). В этом журнале — что изменено и что нужно сделать на сервере.

## 1. Отчёты: провал в цифры, «Мои согласования», «Все согласования»

**Что сделано в демо**

- Новый показатель «Мои согласования»: два блока — «Я — согласующий» (ждут решения, просрочено, согласовано, возвращено на доработку, отклонено, всего) и «Я — инициатор» (в работе, на доработке, согласовано, отклонено, отменено, всего). Каждая цифра открывает список документов, строка списка — карточку.
- В отчёте «Согласования по сотрудникам и подразделениям» все цифры кликабельны и открывают соответствующий список.
- Каждый показатель считается как число различных документов (раньше по сотрудникам считались решения), поэтому цифра всегда совпадает с числом строк в списке. Колонка «Всего решений» переименована в «Всего».
- Новый показатель «Все согласования компании» — только для ролей «Администратор» и «Контроль документов»: все согласования и приказы, включая завершённые, с вкладками по статусу (все, в работе, на доработке, согласовано, отклонено, отменено), поиском и фильтром по виду.
- **Изменение правила доступа:** администратор, как и «Контроль документов», может открыть любую карточку (маршрут, решения, комментарии, файлы, история) в режиме просмотра. Ранее (`docs/02-architecture.md`, решение 6) администратор не имел доступа к содержимому документов.

**Что сделать в основном продукте**

- Сервер: эндпоинты `GET /api/report-ext/my`, `GET /api/report-ext/drill?as=approver|initiator|department&id=&state=`, `GET /api/report-ext/all?state=&kind=&q=` по контракту `web/src/api/reportsExt.ts` (логика — `web/src/demo/reportsExt.ts`); пересчёт `approvals_by_employee` по различным документам; функция доступа к документу — пропуск для роли `admin`; сводка ознакомления доступна администратору.
- Интерфейс: снять флаг `REPORTS_EXT_ENABLED` (сейчас включён только в демо-сборке).
- Обновить `docs/02-architecture.md` (решения 6–7), `docs/04-api.md`, инструкцию администратора; добавить тесты на новые эндпоинты и на доступ администратора.

## 2. Запрос на создание заказа в Битрикс24 по согласованному GPM

**Что сделано в демо**

- В карточке согласования GPM-калькулятора со статусом «Согласовано» и привязанной сделкой инициатор (или администратор) видит призыв «GPM-калькулятор согласован» и кнопку «Запросить создание заказа»; в боковой колонке — блок «Заказ в Битрикс24».
- Окно подтверждения показывает, что уйдёт в Битрикс24: сделку, основание (номер и название согласования), отметку «GPM-калькулятор согласован» с датой и номером запуска, список согласовавших с должностями и датами решений, вложение — последнюю версию Excel-файла калькулятора. Можно добавить комментарий для отдела, создающего заказ (необязательно).
- После отправки в существующем потоке Битрикс24 «Запрос на создание заказа» создаётся элемент, связанный со сделкой: номер, стадия «Новый», отметка о согласовании, таблица согласовавших (ФИО, должность, подразделение, дата, комментарий), файл, комментарий, ссылка на карточку. Он виден на странице сделки и открывается отдельной страницей; файл скачивается.
- По одному согласованию отправляется один запрос: повторная отправка запрещена, в карточке показывается уже отправленный запрос. Событие записывается в историю карточки.
- Если Битрикс24 недоступен, запрос не создаётся, пользователь видит понятную ошибку и может повторить позже; попытка записывается в журнал.
- Отправить могут только инициатор и администратор; согласующие и наблюдатели видят блок в режиме просмотра.

**Что сделать в основном продукте**

- Обследовать поток «Запрос на создание заказа» в кастомизированном Битрикс24: тип сущности (смарт-процесс или иное), идентификатор, поля для отметки «GPM согласован», списка согласовавших, файла, связи со сделкой, стадии.
- Сервер: `GET/POST /api/documents/:id/order-request` по контракту `web/src/api/orderRequest.ts` (логика — `web/src/demo/orderRequests.ts`); в REST-адаптере — создание элемента потока (`crm.item.add` для смарт-процесса), загрузка файла (`disk`/поле файла), привязка к сделке; хранение идентификатора элемента; защита от дублей (маркер `DOCFLOW-ORDER-<id>`).
- Интерфейс: снять флаг `ORDER_REQUEST_ENABLED`.
- Тесты: отправка после согласования, запрет до согласования и для не-GPM, запрет повторной отправки, недоступность Битрикс24, права.
