# Техническое задание

## На разработку внутренней системы документооборота и согласования

**Версия:** 1.0
**Статус:** для согласования перед разработкой
**Этап:** тестовая модель с возможностью дальнейшего развития

---

## 1. Общие сведения

### 1.1. Основание для разработки

Компании необходима система внутреннего документооборота для согласования файлов, оформления приказов и контроля поручений.

Система разрабатывается **с нуля**, размещается на внутреннем сервере компании и интегрируется с действующей кастомизированной версией Битрикс24.

### 1.2. Пользователи

Ориентировочное количество сотрудников компании — **500 человек**.

Расчётное количество одновременно работающих пользователей — **до 150 человек**.

Система должна поддерживать работу следующих подразделений: Sales; IT; Security; Marketing; Finance; юридический отдел; Customer Service; Engineering; Services; Logistics.

Перечень подразделений должен изменяться администратором без доработки программного кода.

### 1.3. Цель разработки

Создать единую внутреннюю систему, в которой сотрудники смогут:

- запускать и проходить согласования;
- прикреплять и хранить файлы;
- оформлять приказы;
- создавать и контролировать поручения;
- видеть историю действий;
- связывать согласования со сделками Битрикс24.

## 2. Разграничение функций с Битрикс24

| Функция | Основная система |
|---|---|
| Работа со сделками | Битрикс24 |
| Операционные задачи по сделкам и проектам | Битрикс24 |
| Согласование GPM-калькулятора и других документов | Система документооборота |
| Оформление и утверждение приказов | Система документооборота |
| Ознакомление с приказами | Система документооборота |
| Поручения, включая самостоятельные | Система документооборота |
| Отображение согласования в сделке | Битрикс24 |
| Хранение истории согласования | Система документооборота |

Система документооборота не должна заменять CRM и полноценный блок операционных задач Битрикс24.

---

## 3. Объём первого этапа

В тестовую модель входят:

1. Авторизация и разграничение прав.
2. Карточки документов и согласований.
3. Согласование GPM-калькулятора.
4. Согласование других документов.
5. Приказы и ознакомление с ними.
6. Поручения, в том числе без документа-основания.
7. Работа с файлами и версиями.
8. Интеграция со сделками Битрикс24.
9. Уведомления.
10. Поиск, списки и базовые отчёты.
11. Журнал действий и администрирование.

В первый этап **не входят**:

- расчёт GPM внутри системы;
- автоматическое определение согласующих по Excel-файлу;
- интеграция согласований с задачами Битрикс24 как отдельными исходными объектами;
- юридически значимая электронная подпись;
- внешнее подписание документов контрагентами.

## 4. Роли и права доступа

### 4.1. Роли пользователей

| Роль | Основные действия |
|---|---|
| **Инициатор** | Создание документа, прикрепление файлов, выбор согласующих, запуск согласования |
| **Согласующий** | Просмотр доступных материалов и принятие решения |
| **Утверждающий** | Утверждение приказа или иного документа |
| **Исполнитель** | Выполнение назначенного поручения |
| **Постановщик поручения** | Создание поручения и контроль результата |
| **Наблюдатель** | Просмотр предоставленных ему документов |
| **Администратор** | Настройка пользователей, подразделений, типов документов и интеграции |

Один сотрудник может совмещать несколько ролей.

### 4.2. Общие правила доступа

1. Доступ к системе предоставляется только авторизованным пользователям.
2. Пользователь видит документы и поручения, к которым ему предоставлен доступ.
3. Доступ может предоставляться по роли, подразделению, участию в процессе или индивидуально.
4. Наличие ссылки на документ не предоставляет доступ без проверки прав.
5. Удаление или блокировка учётной записи не должны удалять историю действий сотрудника.
6. Доступ администратора к содержимому документов должен определяться отдельной настройкой полномочий.

## 5. Авторизация

### 5.1. Тестовая модель

Для тестовой модели допускается использование тестовых учётных записей сотрудников.

Администратор должен иметь возможность:

- создавать и блокировать учётные записи;
- указывать имя сотрудника и подразделение;
- назначать роли;
- сбрасывать пароль.

### 5.2. Дальнейшее развитие

Источник корпоративных учётных записей и необходимость единого входа с Битрикс24 определяются отдельно.

При проектировании необходимо предусмотреть возможность последующего подключения корпоративной системы авторизации.

## 7. Карточка документа и согласования

### 7.1. Общие поля

| Поле | Описание |
|---|---|
| Номер | Уникальный номер карточки |
| Тип | GPM-калькулятор, приказ, другое согласование и т. д. |
| Название | Краткое название документа или согласования |
| Описание | Дополнительная информация от инициатора |
| Инициатор | Сотрудник, создавший карточку |
| Подразделение | Подразделение инициатора |
| Дата создания | Дата и время создания |
| Статус | Текущее состояние процесса |
| Файлы | Основной документ и приложения |
| Участники | Согласующие, утверждающие и наблюдатели |
| Сроки | Общий срок и/или сроки отдельных этапов |
| Связанная сделка | Ссылка и идентификатор сделки Битрикс24 |
| История | Действия, решения, комментарии и изменения |

### 7.2. Название согласования

Инициатор должен иметь возможность:

- ввести название самостоятельно;
- использовать название сделки как основу, если оно доступно через интеграцию;
- изменить предложенное название до запуска согласования.

Название согласования и название сделки должны храниться отдельно.

### 7.3. Черновик

Пользователь должен иметь возможность сохранить карточку как черновик и вернуться к её заполнению позднее.

До запуска согласования система должна проверять обязательные поля.

## 8. Согласование GPM-калькулятора

### 8.1. Назначение

GPM-калькулятор представляет собой **самостоятельный Excel-файл**. Информация о необходимых согласующих определяется сотрудником по данным этого файла.

Система документооборота:

- принимает и хранит файл;
- направляет согласование выбранным сотрудникам;
- фиксирует решения и историю;
- связывает согласование со сделкой Битрикс24.

Система **не рассчитывает GPM**, не анализирует содержимое Excel-файла и не выбирает согласующих автоматически.

### 8.2. Создание согласования

Инициатор должен иметь возможность:

1. Создать карточку типа «Согласование GPM-калькулятора».
2. Ввести название и описание.
3. Выбрать связанную сделку Битрикс24.
4. Прикрепить Excel-файл GPM-калькулятора.
5. При необходимости прикрепить дополнительные файлы.
6. Выбрать согласующих сотрудников.
7. Установить срок согласования.
8. Запустить согласование.

Для запуска обязательны:

- название;
- Excel-файл GPM-калькулятора;
- как минимум один согласующий;
- связанная сделка Битрикс24.

### 8.3. Работа согласующего

Согласующий должен иметь возможность:

- открыть карточку;
- просмотреть сведения о сделке в пределах доступных прав;
- скачать или открыть прикреплённые файлы;
- оставить комментарий;
- согласовать;
- вернуть на доработку;
- отклонить.

При возврате на доработку или отклонении комментарий обязателен.

### 8.4. Доработка

После возврата на доработку инициатор должен иметь возможность:

- ознакомиться с замечаниями;
- загрузить новую версию файла;
- изменить комментарий;
- повторно запустить согласование.

Предыдущие версии файла и принятые по ним решения должны сохраняться.

**Правило тестовой модели:** при повторном запуске согласование начинается заново для всех указанных согласующих. Возможность повторного запуска с отдельного этапа может быть добавлена позднее.

## 9. Другие согласования

Система должна позволять создавать согласования, не относящиеся к GPM-калькулятору.

Для такого согласования инициатор указывает:

- название и описание;
- файл или файлы при необходимости;
- согласующих;
- срок;
- связанную сделку Битрикс24, если она требуется.

Связь со сделкой для обычного согласования не является обязательной, если иное не настроено для конкретного типа документа.

На первом этапе состав типов и их обязательных полей должен настраиваться администратором в пределах реализованных возможностей системы.

## 10. Маршрут согласования

### 10.1. Формирование маршрута

При запуске согласования инициатор вручную выбирает сотрудников.

Система должна предусматривать:

- добавление нескольких согласующих;
- последовательное согласование;
- параллельное согласование;
- установку срока для процесса;
- отображение участников и их решений.

**Порядок по умолчанию и необходимость выбора между последовательным и параллельным режимом при каждом запуске уточняются до реализации.**

### 10.2. Изменение участников

Уполномоченный пользователь должен иметь возможность заменить или добавить согласующего.

Система фиксирует:

- кто изменил маршрут;
- дату и время;
- прежнего и нового участника;
- причину изменения.

Изменение маршрута не должно удалять уже существующую историю решений.

### 10.3. Статусы согласования

| Статус | Значение |
|---|---|
| **Черновик** | Карточка создана, процесс не запущен |
| **На согласовании** | Ожидаются решения согласующих |
| **На доработке** | Документ возвращён инициатору |
| **Согласовано** | Получены все необходимые согласования |
| **Отклонено** | Процесс отклонён |
| **Отменено** | Процесс отменён уполномоченным пользователем |

При последовательном маршруте следующий сотрудник получает документ после согласования предыдущим.

При параллельном маршруте выбранные сотрудники получают документ одновременно. Согласование считается завершённым после положительного решения всех обязательных участников.

## 11. Приказы

### 11.1. Создание

Карточка приказа должна содержать:

- номер и дату;
- название;
- описание;
- инициатора;
- файл приказа и приложения;
- согласующих;
- утверждающего;
- сотрудников, которые должны ознакомиться с приказом;
- связанные поручения;
- статус и историю действий.

### 11.2. Процесс работы

Система должна поддерживать:

1. Создание черновика приказа.
2. Направление на согласование, если оно требуется.
3. Утверждение приказа уполномоченным сотрудником.
4. Направление на ознакомление.
5. Создание поручений по приказу.
6. Архивирование.

### 11.3. Ознакомление

Сотрудник должен иметь возможность открыть приказ и подтвердить ознакомление.

Система фиксирует:

- сотрудника;
- дату и время подтверждения;
- версию приказа, с которой он ознакомился.

Ответственный пользователь должен видеть, кто ознакомился с приказом, а кто нет.

### 11.4. Подписание

На первом этапе **юридически значимая электронная подпись не требуется**.

Утверждение приказа фиксируется как действие авторизованного пользователя. Юридическая значимость такого действия определяется внутренними правилами компании отдельно.

---

## 12. Поручения

### 12.1. Создание

Поручение может быть создано:

- на основании приказа;
- на основании другого документа;
- **самостоятельно, без документа-основания**.

### 12.2. Карточка поручения

Карточка должна содержать:

- номер;
- название и содержание;
- постановщика;
- ответственного исполнителя;
- срок исполнения;
- документ-основание — при наличии;
- статус;
- комментарии;
- файлы;
- результат исполнения;
- историю действий.

### 12.3. Статусы поручения

Предусмотреть как минимум: **Новое**; **В работе**; **На проверке**; **Выполнено**; **Отменено**.

Просрочка должна отображаться отдельно на основании срока и текущего статуса.

### 12.4. Выполнение

Исполнитель должен иметь возможность:

1. Открыть поручение.
2. Указать результат и при необходимости прикрепить файл.
3. Передать результат постановщику на проверку.

Постановщик должен иметь возможность принять результат или вернуть поручение в работу с комментарием.

---

## 13. Работа с файлами

### 13.1. Поддерживаемые форматы

На первом этапе необходимо поддержать загрузку распространённых форматов, включая:

- Excel: XLSX, XLS;
- Word: DOCX, DOC;
- PDF;
- изображения: JPG, JPEG, PNG.

Окончательный перечень разрешённых форматов утверждается совместно с IT и Security.

Для GPM-калькулятора обязательным является прикрепление Excel-файла.

### 13.2. Версии

Система должна:

- хранить предыдущие версии файла;
- показывать дату загрузки и автора версии;
- связывать решения согласующих с версией файла, рассмотренной на соответствующем запуске;
- запрещать незаметную замену файла, находящегося на согласовании.

### 13.3. Ограничения

Максимальный размер одного файла, общий объём вложений и правила проверки файлов определяются до ввода тестовой модели в эксплуатацию.

Скачивание файлов должно быть доступно только пользователям с соответствующими правами.

## 14. Интеграция с Битрикс24

### 14.1. Общие положения

Интеграция выполняется с действующей **кастомизированной версией Битрикс24**.

На первом этапе согласования связываются **только со сделками**. Интеграция с задачами как отдельными объектами для привязки не входит в первый этап.

Перед разработкой необходимо обследовать текущую реализацию Битрикс24: доступные API, доработки сделок, отображение задач и ограничения.

### 14.2. Выбор сделки

При создании согласования пользователь должен иметь возможность выбрать сделку Битрикс24.

Способ выбора — поиск внутри системы документооборота, ввод ссылки или другой механизм — определяется по результатам обследования интеграции.

В карточке согласования сохраняются:

- идентификатор сделки;
- название сделки, если оно доступно;
- ссылка на сделку.

### 14.3. Отображение согласования в сделке

В сделке Битрикс24 согласование должно отображаться **среди задач, привязанных к этой сделке**, в привычном для сотрудников месте.

Запись должна содержать как минимум:

- название согласования;
- текущий статус;
- ссылку на карточку согласования;
- дату создания.

При технической возможности дополнительно отображаются инициатор и текущие согласующие.

### 14.4. Двусторонние ссылки

Должны работать следующие переходы:

1. Из карточки согласования — в связанную сделку Битрикс24.
2. Из записи в сделке — в карточку согласования.

Одна сделка может быть связана с несколькими согласованиями. Каждое согласование должно отображаться отдельной записью со своим статусом.

### 14.5. Передача статуса

Источник статуса — **система документооборота**.

При изменении статуса он должен передаваться в Битрикс24. Как минимум передаются статусы: на согласовании; на доработке; согласовано; отклонено; отменено.

Закрытие или изменение записи в Битрикс24 **не должно само по себе считаться решением согласующих**.

### 14.6. Технический способ отображения

Способ отображения согласования среди задач определяется после обследования Битрикс24. Возможные варианты:

- создание специальной связанной задачи;
- использование существующего кастомного механизма отображения;
- другой способ, сохраняющий привычный вид списка.

Решение должно быть согласовано до реализации. Необходимо избежать создания дублирующих записей при повторной отправке данных.

### 14.7. Ошибки интеграции

Если создание записи или передача статуса не удались, система должна:

- сохранить согласование и его актуальный статус;
- зафиксировать ошибку в журнале;
- показать уполномоченному пользователю состояние синхронизации;
- позволить повторить передачу.

После восстановления связи в Битрикс24 должен передаваться актуальный статус.

---

## 15. Уведомления

Система должна формировать уведомления:

- согласующему — о поступлении документа;
- инициатору — о возврате на доработку, отклонении и завершении согласования;
- утверждающему — о необходимости утвердить документ;
- сотруднику — о необходимости ознакомиться с приказом;
- исполнителю — о назначении поручения;
- постановщику — о передаче результата на проверку;
- участникам — о приближении срока и просрочке, если срок установлен.

Для тестовой модели обязательны **уведомления внутри системы**. Отправка по электронной почте или через Битрикс24 уточняется отдельно.

---

## 16. Поиск и списки

Система должна предоставлять:

- список созданных пользователем документов;
- список согласований, ожидающих решения пользователя;
- список поручений пользователя;
- список документов для ознакомления;
- общий список документов в пределах прав доступа.

Фильтры и поиск должны включать: номер; название; тип; статус; инициатора; подразделение; период создания; связанный номер или название сделки, если они доступны.

---

## 17. Отчёты

На первом этапе должны быть доступны списки и фильтры по следующим показателям:

- согласования в работе;
- согласования с нарушенным сроком;
- документы на доработке;
- поручения в работе;
- просроченные поручения;
- приказы, ожидающие ознакомления;
- согласования по сотруднику и подразделению.

Экспорт отчётов и дополнительные аналитические показатели уточняются отдельно.

---

## 18. История и журналирование

Система должна фиксировать:

- создание и изменение карточки;
- загрузку новой версии файла;
- запуск и повторный запуск согласования;
- решения и комментарии согласующих;
- изменения маршрута;
- утверждение и ознакомление;
- создание и выполнение поручения;
- создание и изменение связи со сделкой;
- ошибки и повторные попытки интеграции.

Для каждой записи фиксируются пользователь или системный процесс, дата, время и выполненное действие.

История должна быть доступна только пользователям с соответствующими правами.

---

## 19. Нефункциональные требования

### 19.1. Размещение

Система размещается на внутреннем сервере компании. Доступ к ней организуется в соответствии с правилами IT и Security.

### 19.2. Пользовательский интерфейс

- Работа через веб-браузер.
- Интерфейс на русском языке.
- Понятное отображение статусов, сроков и ожидаемых действий.
- Возможность перехода из уведомления непосредственно в соответствующую карточку.

Перечень поддерживаемых браузеров согласовывается до разработки.

### 19.3. Производительность

Система проектируется для компании численностью около 500 сотрудников с ориентиром **до 150 одновременных пользователей**.

Конкретные показатели времени отклика, состав нагрузочного теста и конфигурация сервера согласовываются до приёмки.

### 19.4. Безопасность

Необходимо предусмотреть:

- авторизацию и проверку прав на каждое действие;
- защищённую передачу данных;
- защищённое хранение данных для интеграции;
- ограничения доступа к файлам;
- журналирование действий;
- правила проверки загружаемых файлов, согласованные с Security.

### 19.5. Резервное копирование

Необходимо обеспечить резервное копирование базы данных, файлов и необходимых настроек.

Периодичность копирования, сроки хранения копий и допустимое время восстановления определяются совместно с IT.

---

## 20. Администрирование

Администратору должны быть доступны:

- управление пользователями и подразделениями;
- назначение и отзыв ролей;
- настройка типов документов;
- настройка обязательных полей в пределах реализованных возможностей;
- просмотр состояния интеграции;
- просмотр ошибок и повторная отправка данных в Битрикс24;
- управление справочниками;
- просмотр журналов в пределах полномочий.

---

## 21. Требования к документации и результатам разработки

Разработчик передаёт:

1. Исходный код системы.
2. Инструкцию по установке и обновлению.
3. Описание архитектуры и используемых компонентов.
4. Инструкцию администратора.
5. Инструкцию пользователя.
6. Описание интеграции с Битрикс24.
7. Инструкцию по резервному копированию и восстановлению.
8. Перечень настроек и зависимостей.
9. Программу и результаты тестирования.

Порядок передачи исходного кода, лицензии на используемые компоненты и условия сопровождения согласовываются отдельно.

## 22. Критерии приёмки тестовой модели

| № | Сценарий | Ожидаемый результат |
|---|---|---|
| 1 | Пользователь входит под тестовой учётной записью | Доступ предоставлен в соответствии с ролью |
| 2 | Инициатор создаёт GPM-согласование без Excel-файла | Система не позволяет запустить процесс |
| 3 | Инициатор прикрепляет Excel-файл, выбирает сделку и согласующих | Согласование успешно запускается |
| 4 | Согласующий открывает карточку | Доступны сведения и разрешённые файлы |
| 5 | Согласующий возвращает файл на доработку | Инициатор видит комментарий и статус |
| 6 | Инициатор загружает новую версию и повторно запускает процесс | Предыдущая версия и история сохранены |
| 7 | Все обязательные согласующие принимают положительное решение | Согласование получает статус «Согласовано» |
| 8 | Пользователь открывает связанную сделку | Согласование видно среди задач сделки |
| 9 | Пользователь переходит по ссылке из сделки | Открывается нужная карточка после проверки доступа |
| 10 | Статус согласования меняется | Актуальный статус передаётся в Битрикс24 |
| 11 | Передача в Битрикс24 временно недоступна | Ошибка фиксируется; передачу можно повторить без дублирования записи |
| 12 | Пользователь без прав открывает прямую ссылку | Доступ к документу и файлам запрещён |
| 13 | Создаётся приказ с ознакомлением | Система показывает, кто ознакомился и когда |
| 14 | Создаётся самостоятельное поручение | Поручение доступно исполнителю без документа-основания |
| 15 | Исполнитель передаёт результат поручения | Постановщик может принять результат или вернуть его в работу |
| 16 | Пользователь ищет документ по номеру или названию | Отображаются доступные ему результаты |
| 17 | Выполняется проверка восстановления | Данные и файлы восстанавливаются из резервной копии |

До приёмки стороны должны согласовать тестовые данные, условия интеграции и результаты нагрузочного тестирования.
