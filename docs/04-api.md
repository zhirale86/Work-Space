# Справочник API системы документооборота

Источник истины по типам — `server/src/api-types.ts` (файл без импортов, подключается интерфейсом напрямую).
Ниже типы указаны по именам из этого файла. Документ описывает версию сервера из каталога `server/`.

## 1. Общие правила

### 1.1. Адреса и формат

- Все маршруты — с префиксом `/api`; тело запросов и ответов — JSON в UTF-8 (кроме загрузки и скачивания файлов).
- Дата и время — строки ISO 8601 в UTC (`IsoDateTime`, например `2026-11-14T08:30:00.000Z`); дата без времени — `ГГГГ-ММ-ДД` (`IsoDate`).
- Срок (`dueAt`) принимается как ISO-дата-время или как `ГГГГ-ММ-ДД` — тогда это конец указанного дня (23:59:59) по часовому поясу сервера.
- Идентификаторы — целые числа (`Id`), кроме идентификаторов сделок Битрикс24 (строки).
- Списки с разбивкой на страницы: параметры `page` (с 1) и `pageSize` (1–100, по умолчанию 20); ответ `Page<T>` = `{ items, total, page, pageSize }`.
- Логические параметры строки запроса: `true`/`false`/`1`/`0`.
- Неизвестные поля в теле создания и изменения карточек отклоняются (400).
- Ответы API не кэшируются (`Cache-Control: no-store`); на все ответы ставятся заголовки безопасности (`X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, CSP и др.).

### 1.2. Сессия

- Вход — `POST /api/auth/login`; сервер ставит cookie `docflow_session` (`HttpOnly`, `SameSite=Lax`, `Path=/`, `Secure` при `COOKIE_SECURE=true`). Токен в базе хранится только в виде SHA-256.
- Срок сессии — `SESSION_TTL_HOURS` (по умолчанию 12) часов **бездействия**: каждый запрос продлевает сессию (запись в базу — не чаще раза в минуту).
- Без действующей сессии любой маршрут, кроме `POST /api/auth/login` и `GET /api/health`, отвечает 401 `unauthorized`. Интерфейс при 401 показывает страницу входа и после входа возвращает пользователя на исходный адрес (например, на карточку, открытую по ссылке из Битрикс24).
- Неудачные попытки входа: не более 10 на логин за 15 минут, затем 429 `too_many_requests`.
- Ответ на неверный пароль, несуществующий логин и заблокированную запись одинаков: 401 `invalid_credentials`.
- Если администратор выдал временный пароль (`mustChangePassword: true`), до его смены доступны только `/api/auth/*` и `/api/meta`; остальные маршруты отвечают 403 `password_change_required`.
- Блокировка учётной записи, сброс пароля и смена пароля завершают сессии сотрудника (при смене пароля — кроме текущей).

### 1.3. Защита от межсайтовых запросов

Все изменяющие запросы (`POST`, `PUT`, `PATCH`, `DELETE`) к `/api/*`, включая вход, должны содержать заголовок

```
X-Requested-With: docflow
```

Без него — 403 `csrf`. Заголовок не может быть установлен сторонним сайтом без CORS-разрешения, которого сервер не выдаёт; вместе с `SameSite=Lax` это защищает от CSRF. Запросы `GET` заголовка не требуют (ссылки на скачивание файлов работают как обычные ссылки).

### 1.4. Формат ошибок

```json
{ "error": { "code": "unprocessable", "message": "Запуск невозможен: заполните обязательные сведения",
             "details": [ { "field": "mainFile", "message": "Не прикреплён Excel-файл (основной документ)" } ] } }
```

Тип — `ApiErrorBody`. `message` — готовый русский текст для показа пользователю; `details` (необязательно) — перечень замечаний по полям (`ErrorDetail`), интерфейс показывает их списком.

| HTTP | `code` | Когда |
|---|---|---|
| 400 | `validation` | некорректный формат запроса: неизвестное поле, неверный тип, недопустимое значение перечисления; `details[].field` — путь к полю |
| 401 | `unauthorized` | нет действующей сессии |
| 401 | `invalid_credentials` | неверный логин или пароль |
| 403 | `forbidden` | действие не разрешено пользователю (например, решение принимает не согласующий) |
| 403 | `csrf` | нет заголовка `X-Requested-With: docflow` |
| 403 | `password_change_required` | нужно сменить временный пароль |
| 404 | `not_found` | объект не найден **или нет доступа** — существование чужой карточки не раскрывается |
| 409 | `conflict` | действие невозможно в текущем состоянии (раунд завершён, файлы заблокированы на время согласования и т. п.) |
| 413 | `payload_too_large` | файл больше `MAX_FILE_MB` |
| 422 | `unprocessable` | не выполнены требования к данным: пустой обязательный комментарий (в том числе из одних пробелов), незаполненные поля при запуске, недопустимый файл |
| 429 | `too_many_requests` | слишком много неудачных попыток входа |
| 502 | `bitrix_unavailable` | Битрикс24 недоступен при поиске или выборе сделки |
| 500 | `internal` | внутренняя ошибка |

Порядок проверок в действиях с карточками: доступ к карточке (иначе 404) → роль в процессе (403) → состояние процесса (409) → данные (422).

### 1.5. Права (кратко)

Системные роли (`SystemRole`) назначает администратор: `employee`, `signer`, `admin`, `auditor` (подписи — в п. 2). Роли «инициатор», «согласующий», «утверждающий», «наблюдатель», «исполнитель», «постановщик» — контекстные.

**Кто видит документ:** инициатор; согласующие, до которых дошла очередь (шаг был активирован и не заменён), — в любом раунде; утверждающий и наблюдатели — после первого запуска; сотрудники из списка ознакомления — после утверждения приказа; сотрудники и подразделения с индивидуальным доступом; роль `auditor`. Доступ к файлам, истории и комментариям = доступ к карточке. Остальным — 404.

**Кто видит поручение:** постановщик, исполнитель, наблюдатели поручения, роль `auditor`. Участник поручения видит у документа-основания только номер и название (`TaskDocumentRef.accessible` показывает, открывается ли карточка).

**Администратор** (`admin`) без роли `auditor` не получает содержимого документов: ни карточек, ни файлов, ни комментариев. Для управления процессом ему доступны служебные сведения (`/api/admin/documents`), отмена, изменение маршрута, архивирование приказа и повтор передачи в Битрикс24 — в ответ на такие действия он получает `{ ok: true }` вместо карточки.

Списки, счётчики главной страницы и отчёты строятся строго в пределах прав пользователя.

## 2. Перечисления и подписи

Полный перечень с подписями возвращает `GET /api/meta` (`MetaResponse`); интерфейс берёт подписи оттуда или из полей `*Label` ответов.

**Системные роли** `SystemRole`: `employee` — Сотрудник; `signer` — Утверждающий; `admin` — Администратор; `auditor` — Контроль документов.

**Вид документа** `DocKind`: `approval` — Согласование; `order` — Приказ.

**Статус документа** `DocStatus`:

| Код | Согласование | Приказ |
|---|---|---|
| `draft` | Черновик | Черновик |
| `in_review` | На согласовании | На согласовании |
| `rework` | На доработке | На доработке |
| `on_signing` | — | На утверждении |
| `approved` | Согласовано | Утверждён |
| `rejected` | Отклонено | Отклонён |
| `cancelled` | Отменено | Отменён |
| `archived` | — | В архиве |

Переходы: `draft` → `in_review` (запуск; приказ без согласующих — сразу `on_signing`) → `approved` (все согласовали; приказ — `on_signing`) | `rework` (возврат) | `rejected` (отклонение); `rework` → `in_review` (повторный запуск); `on_signing` → `approved` | `rework` | `rejected`; приказ `approved` → `archived`; из `draft`, `in_review`, `rework`, `on_signing` — `cancelled`.

**Режим маршрута** `RouteMode`: `sequential` — Последовательное; `parallel` — Параллельное.

**Итог раунда** `RoundOutcome`: `approved` — Согласовано; `rework` — Возвращено на доработку; `rejected` — Отклонено; `cancelled` — Отменено.

**Состояние шага** `StepState`: `waiting` — Очередь не дошла; `pending` — Ожидается решение; `approved` — Согласовано; `rework` — Возвращено на доработку; `rejected` — Отклонено; `skipped` — Не потребовалось; `replaced` — Участник заменён.

**Решение** `Decision`: `approve` — Согласовать; `rework` — Вернуть на доработку; `reject` — Отклонить.

**Ожидаемое от меня действие** `MyDocumentAction`: `approve` — Ожидает вашего решения; `sign` — Ожидает вашего утверждения; `acknowledge` — Требуется ознакомление; `rework` — Требуется доработка; `null` — ничего.

**Статус поручения** `TaskStatus`: `new` — Новое; `in_progress` — В работе; `review` — На проверке; `done` — Выполнено; `cancelled` — Отменено. Признак `overdue` («просрочено») вычисляется: срок прошёл, статус не `done`/`cancelled`. Для документа `overdue` — срок прошёл в статусах `in_review`, `on_signing`, `rework`.

**Роль файла** `FileRole`: `main` — Основной документ; `attachment` — Приложение; `result` — Результат исполнения (только поручения).

**Передача в Битрикс24** `BitrixLinkState`: `pending` — Ожидает передачи; `synced` — Передано; `error` — Ошибка передачи. Задача эмулятора `MockTaskStatus`: `in_progress` — Выполняется; `completed` — Завершена.

**Типы уведомлений** `NotificationType`: `approval_requested` — Документ на согласование; `approval_rework` — Возврат на доработку; `approval_rejected` — Отклонение; `approval_completed` — Согласование завершено; `approval_cancelled` — Процесс отменён; `sign_requested` — Приказ на утверждение; `order_signed` — Приказ утверждён; `acknowledge_requested` — Ознакомление с приказом; `route_changed` — Изменение маршрута; `reminder` — Напоминание; `participant_blocked` — Требуется замена участника; `task_assigned` — Новое поручение; `task_submitted` — Результат на проверку; `task_accepted` — Поручение принято; `task_returned` — Поручение возвращено в работу; `task_cancelled` — Поручение отменено; `task_changed` — Поручение изменено; `deadline_soon` — Срок приближается; `deadline_overdue` — Срок нарушен; `comment_added` — Новый комментарий.

**Отчёты** `ReportCode`: `approvals_in_progress` — Согласования в работе; `approvals_overdue` — Согласования с нарушенным сроком; `documents_rework` — Документы на доработке; `tasks_in_progress` — Поручения в работе; `tasks_overdue` — Просроченные поручения; `orders_pending_acknowledgement` — Приказы, ожидающие ознакомления; `approvals_by_employee` — Согласования по сотрудникам; `approvals_by_department` — Согласования по подразделениям.

## 3. Служебные маршруты

| Маршрут | Кто | Ответ |
|---|---|---|
| `GET /api/health` | без сессии | `{ ok: true }` — приложение и база доступны (500 — нет связи с базой) |
| `GET /api/meta` | любой вошедший (в т. ч. до смены временного пароля) | `MetaResponse`: перечисления с подписями, `limits` (`maxFileMb`, `maxFilesPerCard`, `maxCardTotalMb`, `allowedExtensions`), `bitrixMode` |

## 4. Сессия

### `POST /api/auth/login`
Без сессии. Тело `LoginRequest` `{ login, password }` (логин без учёта регистра). Ответ `LoginResponse` `{ user: CurrentUser }` и cookie сессии.
Ошибки: 400; 401 `invalid_credentials`; 429.

### `POST /api/auth/logout`
Вошедший. Тело `{}`. Завершает текущую сессию, очищает cookie. Ответ `OkResponse`.

### `GET /api/auth/me`
Вошедший. Ответ `MeResponse` `{ user: CurrentUser }` (`roles`, `roleLabels`, `mustChangePassword`, подразделение).

### `POST /api/auth/change-password`
Вошедший. Тело `ChangePasswordRequest` `{ currentPassword, newPassword }` (новый — не короче 8 символов). Снимает признак временного пароля, завершает остальные сессии. Ответ `OkResponse`.
Ошибки: 422 (неверный текущий пароль — `details[].field = currentPassword`; короткий новый — `newPassword`).

## 5. Справочники

### `GET /api/users`
Вошедший. Поиск **активных** сотрудников для выбора участников (заблокированные не предлагаются). Параметры `UsersQuery`: `q` (ФИО, логин, должность), `departmentId`, `role` (например `signer` — для выбора утверждающего), `page`, `pageSize`. Ответ `Page<UserRef>`.

### `GET /api/departments`
Вошедший. Действующие подразделения. Ответ `{ items: Department[] }`.

### `GET /api/doc-types`
Вошедший. Действующие типы документов с настройками обязательности (`requireDeal`, `requireFile`, `requireExcel`, `requireDeadline`, `requireDescription`). Ответ `{ items: DocType[] }`.

## 6. Главная страница и отчёты

### `GET /api/dashboard`
Вошедший. Ответ `DashboardResponse`: блоки `toApprove`, `rework`, `toSign`, `toAcknowledge` (`DashboardBlock<DocumentListItem>`), `myTasks`, `tasksToReview` (`DashboardBlock<TaskListItem>`) — по каждому `count` и до 5 первых записей; `overdue` — просроченное, по которому действие ожидается от меня (`{ count, documents, tasks }`); `unreadNotifications`.

### `GET /api/reports/summary`
Вошедший. Количество записей по каждому отчёту в пределах прав пользователя. Ответ `ReportSummaryResponse`.

### `GET /api/reports/:reportCode`
Вошедший. `reportCode` — `ReportCode`. Параметры `ReportQuery`: `userId` (для `approvals_by_employee` — согласующий; для документных отчётов — инициатор; для поручений — исполнитель), `departmentId`, `page`, `pageSize`. Ответ `ReportResponse` (поле `code` определяет тип элементов):
- `approvals_in_progress` (статусы `in_review`, `on_signing`), `approvals_overdue` (только незавершённые с прошедшим сроком), `documents_rework` → `Page<DocumentListItem>`;
- `tasks_in_progress` (`new`, `in_progress`, `review`), `tasks_overdue` → `Page<TaskListItem>`;
- `orders_pending_acknowledgement` → `Page<OrderAcknowledgementReportItem>` (`ackTotal`, `ackDone`, `ackPending`); видны приказы, где я инициатор или утверждающий (роль `auditor` — все);
- `approvals_by_employee` → `Page<ApprovalsByEmployeeItem>`; `approvals_by_department` → `Page<ApprovalsByDepartmentItem>`.
Ошибки: 404 — неизвестный отчёт.

## 7. Документы (согласования и приказы)

### `GET /api/documents`
Вошедший. Только доступные документы. Параметры `DocumentsQuery`:
`q` — номер, название, название сделки (без учёта регистра, вхождение); `scope` — `all` (по умолчанию), `mine` (я инициатор), `to_approve` (ждёт моего решения), `to_sign` (ждёт моего утверждения), `to_acknowledge` (мне нужно ознакомиться); `kind`; `typeId`; `status` — один или несколько через запятую; `initiatorId`; `departmentId` (подразделение инициатора на момент создания); `createdFrom`, `createdTo` (`ГГГГ-ММ-ДД`, включительно); `deal` — идентификатор или часть названия сделки; `overdue`; `page`, `pageSize`.
Ответ `Page<DocumentListItem>` (сортировка — новые сначала). Поле `myAction` — действие, ожидаемое от текущего пользователя.
Ошибки: 400 — недопустимый статус или параметр.

### `POST /api/documents`
Вошедший (становится инициатором). Тело `CreateDocumentRequest`: `typeId` (обязательно); `title`, `description`, `dueAt`, `routeMode` (по умолчанию `sequential`); `dealId` — только для согласований; `approverIds` — в порядке маршрута; `observerIds`; для приказа — `signerId` (сотрудник с ролью `signer`), `acquaintanceIds`, `orderDate`.
Создаётся черновик, номер присваивается сразу: `<префикс типа>-<год>-<6 цифр>` (`GPM-2026-000014`, `СГЛ-…`, `ПР-…`), отдельный счётчик на префикс и год. При `dealId` сервер получает название и ссылку сделки у Битрикс24 и сохраняет их отдельно от названия согласования.
Ответ 201 `DocumentDetail`.
Ошибки: 400; 422 — тип не найден или отключён, сотрудник не найден или заблокирован, инициатор указан согласующим, сотрудник указан согласующим дважды, утверждающий без роли `signer`, сделка для приказа, поля приказа для согласования, сделка не найдена; 502 — Битрикс24 недоступен.

### `GET /api/documents/:id`
Доступ к карточке (п. 1.5). Ответ `DocumentDetail`: поля карточки; `approvers` (плановый состав для следующего запуска), `observers`, `acquaintance`; `rounds` — раунды от нового к старому, у каждого `steps` и `files` (снимок версий файлов, рассмотренных в раунде); `files` — действующие файлы со всеми версиями; `myStep`, `myAction`, `myAcknowledgement`; `acknowledgements` — сводка ознакомления (только инициатору, утверждающему и `auditor`, иначе `null`); `access` — индивидуальный доступ (инициатору и `auditor`); `tasks` — доступные мне поручения по документу; `bitrix` — состояние передачи в Битрикс24 (`null`, если сделки нет или процесс не запускался); `comments`; `permissions` (`DocumentPermissions`) — что показывать в интерфейсе.
Ошибки: 404.

### `PATCH /api/documents/:id`
Инициатор; статусы `draft`, `rework`. Тело `UpdateDocumentRequest` — любые поля `CreateDocumentRequest`, кроме `typeId`; изменяются только переданные. Сделку можно менять только до первого запуска (`dealLocked`). Изменения пишутся в историю.
Ответ `DocumentDetail`. Ошибки: 403 — не инициатор; 404; 409 — недопустимый статус или сделка после запуска; 422 — как при создании; 502.

### `DELETE /api/documents/:id`
Инициатор; только черновик, ни разу не запускавшийся. Удаляет карточку и её файлы. Ответ `OkResponse`. Ошибки: 403, 404, 409.

### `POST /api/documents/:id/copy`
Инициатор исходной карточки (в любом статусе, в том числе отклонённой или отменённой). Создаёт новый черновик с теми же полями и участниками — без файлов, решений и срока; заблокированные участники не переносятся. Ответ 201 `DocumentDetail` (новая карточка). Ошибки: 403, 404, 409 — тип отключён.

### `PUT /api/documents/:id/access`
Инициатор. Тело `AccessRequest` `{ userIds, departmentIds }` — полный новый перечень индивидуального доступа на просмотр. Ответ `DocumentDetail`. Ошибки: 403, 404, 422 — сотрудник заблокирован или подразделение не найдено.

### `GET /api/documents/:id/history`
Доступ к карточке. Параметры `page`, `pageSize` (по умолчанию 50). Ответ `Page<HistoryEntry>` — от новых к старым; `actor = null`, `actorName = «Системный процесс»` — действия фоновых заданий (передача в Битрикс24, автоматическое завершение раунда). Фиксируются: создание и изменение карточки, файлы и версии, запуск и повторный запуск, решения и комментарии, изменение маршрута, утверждение и ознакомление, поручения по документу, связь со сделкой, ошибки и повторы передачи в Битрикс24.

### `GET /api/documents/:id/comments`
Доступ к карточке. Ответ `{ items: Comment[] }` (по возрастанию времени).

### `POST /api/documents/:id/comments`
Доступ к карточке. Тело `AddCommentRequest` `{ body }` (до 5000 символов). Инициатор и участники, от которых ожидается решение, получают уведомление. Ответ 201 `Comment`. Ошибки: 404; 422 — пустой комментарий.

## 8. Процесс согласования

### `POST /api/documents/:id/launch`
Инициатор; статусы `draft` (запуск) и `rework` (повторный запуск). Тело `LaunchRequest` `{ routeMode? }` — если передан, сохраняется как режим маршрута.
Проверки (все замечания возвращаются сразу в `details`): название (`title`); согласующие (`approvers`) — хотя бы один для согласования, без заблокированных и без инициатора; утверждающий (`signer`) для приказа — активный, с ролью `signer`; поля по настройкам типа — `deal`, `description`, `dueAt`, `mainFile` (для `requireExcel` — основной файл XLSX или XLS); срок не в прошлом (`dueAt`: «Срок уже прошёл — укажите новый срок»).
Создаётся новый раунд для **всех** согласующих; фиксируется снимок текущих версий файлов. Последовательный режим: первый шаг `pending`, остальные `waiting`; параллельный — все `pending`. Приказ без согласующих сразу переходит в `on_signing`. Получатели документа уведомляются; при наличии сделки документ ставится в очередь передачи в Битрикс24.
Ответ `DocumentDetail`. Ошибки: 403 — не инициатор; 404; 409 — недопустимый статус; 422 — замечания.

### `POST /api/documents/:id/decision`
Согласующий с шагом `pending` в текущем раунде. Тело `DecisionRequest` `{ decision, comment? }`; при `rework` и `reject` комментарий обязателен (строка из пробелов считается пустой).
Согласование: в последовательном режиме документ получает следующий участник, после последнего — статус `approved` (приказ — `on_signing`). Отрицательное решение сразу завершает раунд: `rework` → «На доработке», `reject` → «Отклонено»; шаги, не успевшие ответить, — `skipped`. Решения сериализуются блокировкой: при одновременных решениях итог один.
Повтор того же решения тем же участником (двойное нажатие) возвращает карточку без второй записи. Ответ `DocumentDetail`.
Ошибки: 400 — неизвестное решение; 403 — нет шага в текущем раунде; 404; 409 — раунд завершён, очередь не дошла, решение по шагу уже принято (другое); 422 — нет комментария.

### `PUT /api/documents/:id/route`
Инициатор или администратор; статус `in_review`. Тело `RouteChangeRequest`:
- `{ action: 'replace', fromUserId, toUserId, reason }` — заменить участника, ещё не принявшего решение (`pending` или `waiting`); новый участник занимает его место в очереди; заменённый теряет доступ к карточке и файлам, если нет других оснований;
- `{ action: 'add', toUserId, reason }` — добавить в конец маршрута (в параллельном — сразу получает документ).
Причина обязательна; изменение (кто, когда, прежний и новый участник, причина) пишется в историю; плановый состав для следующего запуска обновляется.
Ответ `DocumentDetail` (администратору без роли `auditor` — `OkResponse`).
Ошибки: 403; 404; 409 — завершённый документ, не `in_review`, заменяемый уже принял решение; 422 — нет причины, сотрудник заблокирован, не найден, уже в маршруте, является инициатором.

### `POST /api/documents/:id/cancel`
Инициатор или администратор; статусы `draft`, `in_review`, `rework`, `on_signing`. Тело `CancelRequest` `{ reason }` (обязательно). Ожидающие участники и инициатор уведомляются. Повторная отмена отменённого — без изменений. Ответ `DocumentDetail` или `OkResponse` (администратор без `auditor`). Ошибки: 403, 404, 409, 422.

### `POST /api/documents/:id/remind`
Инициатор; статусы `in_review` (участникам с шагом `pending`) и `on_signing` (утверждающему). Не чаще раза в сутки (`permissions.canRemind`). Тело `{}`. Ответ `DocumentDetail`. Ошибки: 403, 404, 409.

## 9. Приказы

### `POST /api/documents/:id/sign`
Утверждающий, указанный в приказе; статус `on_signing`. Тело `SignRequest` (= `DecisionRequest`): `approve` → «Утверждён» (проставляются `signedAt` и, если не задана, `orderDate`; сотрудники из списка ознакомления получают уведомления), `rework` → «На доработке», `reject` → «Отклонён»; для `rework`/`reject` комментарий обязателен. Повтор того же решения — без изменений. Ответ `DocumentDetail`.
Ошибки: 403 — не утверждающий; 404; 409 — не на утверждении или не приказ; 422 — нет комментария.

### `POST /api/documents/:id/acknowledge`
Сотрудник из списка ознакомления; только утверждённый приказ (`approved`). Фиксируются время и версия основного файла. Повторное подтверждение ничего не меняет. Тело `{}`. Ответ `DocumentDetail`.
Ошибки: 403 — не в списке; 404 — приказ ещё не виден сотруднику (до утверждения); 409 — приказ не утверждён или в архиве.

### `PUT /api/documents/:id/acquaintance`
Инициатор приказа; кроме статусов `rejected`, `cancelled`, `archived`. Тело `AcquaintanceRequest` `{ userIds }` — полный перечень; после утверждения список можно только дополнять (добавленные получают уведомление). Ответ `DocumentDetail`. Ошибки: 403, 404, 409 — сокращение после утверждения; 422 — сотрудник заблокирован.

### `POST /api/documents/:id/archive`
Инициатор или администратор; утверждённый приказ. Тело `{}`. Ответ `DocumentDetail` или `OkResponse`. Ошибки: 403, 404, 409.

Сводка ознакомления (`DocumentDetail.acknowledgements`, `AcknowledgementSummary`) доступна инициатору, утверждающему и роли `auditor`: `total` — ожидается подтверждений (заблокированные, не успевшие ознакомиться, не учитываются), `acknowledged`, `pending`, `items` — по каждому сотруднику время и версия файла.

## 10. Файлы

Разрешённые расширения — `ALLOWED_EXTENSIONS` (по умолчанию `xlsx, xls, docx, doc, pdf, jpg, jpeg, png`); проверяются расширение и сигнатура содержимого (XLSX/DOCX — ZIP-контейнер с соответствующей частью, XLS/DOC — OLE, PDF, JPEG, PNG). Файлы с макросами (`xlsm`, `docm`, `xlsb` и др., а также XLSX/DOCX с `vbaProject.bin`) отклоняются. Ограничения: файл — `MAX_FILE_MB` (50 МБ), карточка — `MAX_FILES_PER_CARD` (20) файлов и `MAX_CARD_TOTAL_MB` (200 МБ). На диске файлы хранятся под случайными именами; отдаются только через API с проверкой прав.

Загрузка — `multipart/form-data`, один файл в поле `file`; имя файла берётся из части (UTF-8). Ответ — `FileItem` (файл со всеми версиями).

### `POST /api/documents/:id/files?role=main|attachment&title=`
Инициатор; статусы `draft`, `rework`. `role` — `attachment` по умолчанию; основной документ (`main`) в карточке один — замена выполняется новой версией. Ответ 201 `FileItem`.

### `POST /api/files/:fileId/versions`
Как загрузка в карточку документа (инициатор, `draft`/`rework`); для поручения — сотрудник, прикрепивший файл, пока поручение не завершено. Предыдущие версии сохраняются, решения прошлых раундов остаются привязанными к рассмотренным версиям. Ответ 201 `FileItem`.

### `DELETE /api/files/:fileId`
Те же права. Файл помечается удалённым и исчезает из карточки; версии остаются в снимках раундов и в истории. Ответ `OkResponse`.

### `POST /api/tasks/:id/files?role=attachment|result&title=`
Постановщик или исполнитель незавершённого поручения; `result` — только исполнитель. Ответ 201 `FileItem`.

### `GET /api/file-versions/:id/download`
Доступ к карточке-владельцу (документу или поручению). Ответ — содержимое файла с заголовками `Content-Disposition: attachment; filename="…"; filename*=UTF-8''…`, `Content-Type` по расширению, `X-Content-Type-Options: nosniff`, `Cache-Control: private, no-store`. Предпросмотра в браузере нет.

Ошибки загрузки и скачивания: 400 — не multipart или нет поля `file`; 403 — нет роли; 404 — нет доступа к карточке или файлу; 409 — документ на согласовании/утверждении или завершён, второй основной документ; 413 — превышен размер файла; 422 — недопустимый тип, несоответствие содержимого расширению, макросы, пустой файл, превышено количество или общий объём файлов карточки.

## 13. Битрикс24

### `GET /api/bitrix/deals?q=`
Вошедший. Поиск сделок по названию и номеру для выбора в карточке (до 20). Ответ `DealsResponse` `{ items: Deal[] }`. Ошибки: 502 `bitrix_unavailable`.

### `GET /api/bitrix/deals/:id`
Вошедший. Сведения о сделке: только `id`, `title`, `url` (права сотрудника в Битрикс24 системе неизвестны). Ответ `Deal`. Ошибки: 400 — некорректный идентификатор; 404; 502.

### `POST /api/documents/:id/bitrix/retry`
Инициатор или администратор. Немедленный повтор передачи **актуального** состояния документа в Битрикс24. Повтор не создаёт дубля: если идентификатор записи неизвестен, адаптер сначала ищет её по маркеру `DOCFLOW-<id документа>`. Тело `{}`. Ответ `BitrixRetryResponse` `{ bitrix: BitrixLinkInfo }`. Ошибки: 403; 404; 409 — по документу нет записи передачи (нет сделки или процесс не запускался).

Как работает передача: при запуске согласования со сделкой и при каждом изменении статуса или текущих согласующих документ ставится в очередь; попытка выполняется сразу после изменения и фоновым заданием каждые 15 с. Передаётся целевое состояние, а не событие: сколько бы раз статус ни сменился за время недоступности, после восстановления в сделке окажется одна запись с последним статусом. При ошибке — `state = error`, текст ошибки, запись в журнал и автоматический повтор через 1, 5, 15, 60 минут. Удалённая в Битрикс24 запись создаётся заново, закрытая при активном согласовании — возобновляется. Запись закрывается при статусах «Согласовано», «Отклонено», «Отменено». Изменение записи в Битрикс24 не влияет на согласование. Черновики и приказы не передаются.

Запись в сделке: название `[<статус>] <название согласования>`; описание — номер, статус, ссылка на карточку (`PUBLIC_URL/documents/<id>`), инициатор, текущие согласующие, дата создания.

- `GET /api/admin/documents` — параметры `AdminDocumentsQuery` (`q` — номер, `status`, `initiatorId`, `page`, `pageSize`). Ответ `Page<AdminDocumentItem>` — без названия и содержимого; черновики не показываются.
- `GET /api/admin/documents/:id` — `AdminDocumentDetail`: режим маршрута, утверждающий, шаги текущего раунда (без комментариев), состояние передачи в Битрикс24, доступные управляющие действия (`canCancel`, `canChangeRoute`, `canArchive`). Ошибки: 404.

Управляющие действия администратор выполняет обычными маршрутами (`/cancel`, `/route`, `/archive`, `/bitrix/retry`) — в ответ `OkResponse`, если у него нет роли `auditor`.
